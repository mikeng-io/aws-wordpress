A faster disk did nothing. The protocol was everything.

Three storage tiers, one benchmark, 60,300 timed syscalls across 3 independent deployments. Attached NVMe, a network block device and Fargate's ephemeral volume came out within 1.5× of each other. EFS sat 638× away.

Latency spans microseconds to milliseconds, so the axis is log-10. The marks fall into two bands with nothing in between — that gap is the finding.

1.00×

Predicted: 118 GB of attached NVMe rated 33,542 IOPS would beat a network-attached EBS volume on the operations that reach a device. It did not — on any of them, tails included.

The working set is ~50 MB against 4 GiB of RAM, so after the first pass the kernel answers from cache and the disk is never consulted. A faster device cannot speed up an operation that never reaches it.

Why EFS is different — it is two distributions

EBS is also on the far end of a wire. The difference is not distance, it is what sits at the other end: EBS is a block device, so your own kernel runs the filesystem and owns the metadata. EFS is a file protocol, so the server owns it and your kernel has to ask.

It only sometimes has to ask. The NFS attribute cache absorbs roughly 30% of lookups — the left spike, sitting exactly on top of the block-backed tiers. The other 70% go to the wire, and that is the whole gap.
